Guillermo had a contact card with three buttons. Two of them worked. "Email Pablo" opened a form. "LinkedIn" opened my profile. "Schedule a Call" just sat there doing nothing for weeks.

The obvious fix was Calendly's REST API or their embed widget. But then I noticed something: Calendly has a remote MCP server at `mcp.calendly.com`. Not a local server you run in your terminal. A real, hosted remote server using Streamable HTTP transport.

I'd been using MCP in dev tools (Claude Desktop, Cursor) but never in a production web app. This felt like a chance to actually build with the protocol, not just consume it through an IDE.

Spoiler: MCP didn't make it to production. REST API did.

## MCP in 30 seconds

If you already know what MCP is, skip ahead. If not, here's the short version.

Model Context Protocol is a standardized way for AI applications to use external tools. Any MCP-compatible client can connect to any MCP-compatible server and use its tools, without custom integration code for each service.

Most people encounter MCP through local servers. You configure one in Claude Desktop or Cursor, it runs as a subprocess over stdio, and your AI assistant gets new abilities.

Remote MCP servers are different. They live on the internet, use HTTP-based transport, and require real authentication. That's what Calendly offers at `mcp.calendly.com`. The standard flow: connect to the server, call `listTools()` to discover what's available, pass those tools to the LLM, let the LLM call them as needed.

So that's the theory. Here's what I built.

## The architecture I built

The flow has two distinct layers that are easy to conflate:

```
LLM calls checkAvailability          <-- AI SDK layer (the LLM's world)
  └── execute() runs
        └── fetchAvailableSlots()    <-- MCP layer starts here
              └── callCalendlyMCP()
                    └── StreamableHTTPClientTransport → mcp.calendly.com
```

The LLM doesn't know MCP exists. It calls an AI SDK tool, and that tool's `execute()` function happens to use MCP internally.

### OAuth setup: Dynamic Client Registration

Calendly's MCP server uses OAuth 2.1 with PKCE and Dynamic Client Registration. No pre-registered app, no client secret, no dashboard configuration. The client registers itself at auth time.

I wrote a one-time setup script that runs locally:

```javascript
// scripts/calendly-auth.mjs (trimmed)

const clientMetadata = {
  client_name: "dimeglio-dev Guillermo Agent",
  redirect_uris: ["http://localhost:8549/callback"],
  grant_types: ["authorization_code", "refresh_token"],
  scope: "mcp:scheduling:read mcp:scheduling:write",
  token_endpoint_auth_method: "none",
};

const res = await fetch(metadata.registration_endpoint, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(clientMetadata),
});
const clientInfo = await res.json();
```

The script opens a browser for authorization, catches the callback on a local server, exchanges the code for tokens (with PKCE), and stores everything in Upstash Redis. Tokens live in Redis, not on disk. Both local dev and Vercel production read from the same place. Run it once and you're done.

### Token management: Redis + optimistic locking

The tokens expire. In a serverless environment, two requests might try to refresh at the same time. I used Redis `SET NX EX` as a lock:

```typescript
// lib/calendly-mcp.ts — getValidAccessToken() (trimmed)

const tokens = await readTokens();
if (!isExpired(tokens)) return tokens.access_token;

const lockAcquired = await redis.set(REDIS_KEY_LOCK, "1", { nx: true, ex: 10 });

if (!lockAcquired) {
  await new Promise((r) => setTimeout(r, 2000));
  return (await readTokens())?.access_token ?? null;
}

const newTokens = await refreshAuthorization(CALENDLY_AUTH_SERVER_URL, {
  metadata,
  clientInformation: clientInfo,
  refreshToken: tokens.refresh_token,
});
await writeTokens({ ...newTokens, obtained_at: Date.now() });
```

### The MCP call: connect, call, disconnect

Each MCP call is a fresh connection:

```typescript
// lib/calendly-mcp.ts — callCalendlyMCP() (trimmed)

const transport = new StreamableHTTPClientTransport(
  new URL("https://mcp.calendly.com"),
  { requestInit: { headers: { Authorization: `Bearer ${accessToken}` } } }
);

const client = new Client(
  { name: "dimeglio-dev-guillermo", version: "1.0.0" },
  { capabilities: {} }
);

await client.connect(transport);
const result = await client.callTool({ name: toolName, arguments: args });
await client.close();
```

Worked great locally.

## Where it fell apart on Vercel

I deployed, clicked "Schedule a Call" in the chat, and got a 504.

Not a clean error. Not a helpful message. Just Vercel timing out the function after 10 seconds with no response.

Three things were working against me:

**1. `StreamableHTTPClientTransport` owns the `AbortSignal`.**
The SDK's transport layer overwrites whatever `AbortSignal` you pass with its own internal controller. There's no way to set a timeout on the connection from the outside. If `mcp.calendly.com` takes 11 seconds to respond, your Vercel function sits and waits until Vercel kills it.

**2. SSE streams don't flush reliably through Vercel's network layer.**
Streamable HTTP uses Server-Sent Events for the response. SSE expects a persistent, flushing connection. Vercel's serverless infrastructure buffers responses and isn't designed for that pattern. The connection would open and then just... hang. No data, no error, no timeout. Vercel eventually gave up.

**3. This isn't a bug I could fix.**
Both of these are fundamental to how Streamable HTTP transport works. It's designed for long-running services with persistent connections, not for serverless functions that spin up, do one thing, and die. I could have worked around it with a proxy or a custom transport, but at that point I was solving an infrastructure problem just to avoid a direct API call.

Anyway, I switched to the REST API.

## What actually shipped

Calendly has a REST API and supports Personal Access Tokens. Swapping out the MCP transport for a direct `fetch` call took about 20 minutes:

```typescript
// lib/calendly.ts — what actually runs in production

async function fetchAvailableSlots(): Promise<string[] | null> {
  const res = await fetch(
    `https://api.calendly.com/event_type_available_times?` +
    `event_type=${encodeURIComponent(EVENT_TYPE_URI)}&` +
    `start_time=${startTime}&end_time=${endTime}`,
    {
      headers: { Authorization: `Bearer ${process.env.CALENDLY_API_TOKEN}` },
      signal: AbortSignal.timeout(5000), // actually works
    }
  );
  if (!res.ok) return null;
  const data = await res.json();
  return data.collection.map((s: { start_time: string }) => s.start_time);
}
```

No OAuth dance, no Redis, no connection lifecycle. `AbortSignal.timeout(5000)` works because I control the fetch, not a transport layer.

Both the auth script and MCP client are still in the repo for when Guillermo moves off serverless.

## The parts I'd have hit either way

Switching to REST didn't change everything. A few Calendly gotchas that apply either way:

**No time pre-selection on single-use links.** I expected to generate a scheduling link that opens Calendly on the exact time slot the user picked. What actually happens: Calendly's single-use links (`/d/xxxx`) ignore all time-related URL parameters. I tried `?time=09:30` (silently ignored), path-based ISO timestamps (also ignored). Only `?date=YYYY-MM-DD` works. One extra click for the user: "Select 9:30 AM on Calendly to confirm."

**No direct booking on the free plan.** The `create_invitee` endpoint would let Guillermo book the slot on behalf of the user. Not available on the free plan. Workaround: single-use scheduling links. The slot isn't held between when the user clicks and when they complete booking. Someone else could theoretically grab it. The "single-use" property is about the link, not the slot.

**Availability window: 7 days max, start time must be in the future.** The API returns 400 for windows longer than 7 days. `new Date().toISOString()` is "in the past" by the time the request arrives. Add a 5-minute buffer.

## The small model prompt problem

After switching to REST and getting the widget rendering, there was still a prompt issue. The system prompt said "do NOT describe time slots as text." GPT-4o-mini, the model powering Guillermo, dutifully listed every time slot as text.

Negative constraints don't work well with small models. The fix was telling it exactly what to say instead: "Your text response must be exactly one short sentence like 'Here are Pablo's available slots.'" That worked.

## What I'd actually tell someone evaluating MCP for production

MCP works in production. The `@modelcontextprotocol/sdk` is well-built. OAuth 2.1 with Dynamic Client Registration, Streamable HTTP transport, tool discovery. It all works as documented.

What didn't work was my specific combination: Streamable HTTP transport inside Vercel serverless functions. SSE-based persistent connections and functions that spin up per request and die are a bad pair. That's not a MCP problem. It's an environment problem I created for myself.

The MCP code is still in the repo. I'll revisit when Guillermo moves off serverless.

The "Schedule a Call" button works. Most of that day was me and a bad environment combination.
