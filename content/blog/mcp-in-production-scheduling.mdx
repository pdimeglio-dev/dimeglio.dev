Guillermo had a contact card with three buttons. Two of them worked. "Email Pablo" opened a form. "LinkedIn" opened my profile. "Schedule a Call" just sat there doing nothing for weeks.

The obvious fix was Calendly's REST API or their embed widget. But then I noticed something: Calendly has a remote MCP server at `mcp.calendly.com`. Not a local server you run in your terminal. A real, hosted remote server using Streamable HTTP transport.

I'd been using MCP in dev tools (Claude Desktop, Cursor) but never in a production web app. This felt like a chance to try something different and actually build with the protocol, not just consume it through an IDE.

## MCP in 30 seconds

If you already know what MCP is, skip ahead. If not, here's the short version.

Model Context Protocol is a standardized way for AI applications to use external tools. Think of it as a USB port for AI capabilities: any MCP-compatible client can connect to any MCP-compatible server and use its tools, without custom integration code for each service.

Most people encounter MCP through local servers. You configure one in Claude Desktop or Cursor, it runs as a subprocess communicating over stdio, and your AI assistant gets new abilities (file access, database queries, whatever the server exposes).

Remote MCP servers are different. They live on the internet, use HTTP-based transport, and require real authentication. That's what Calendly offers at `mcp.calendly.com`.

The standard MCP flow looks like this: connect to the server, call `listTools()` to discover what's available, pass those tools to the LLM, and let the LLM call them as needed. Clean, dynamic, protocol-native.

That's the textbook version. Here's what I actually built.

## The architecture

The flow has two distinct layers that are easy to conflate. Making them explicit is the single most important thing for understanding what's happening:

```
LLM calls checkAvailability          <-- AI SDK layer (the LLM's world)
  └── execute() runs
        └── fetchAvailableSlots()    <-- MCP layer starts here
              └── callCalendlyMCP()
                    └── StreamableHTTPClientTransport → mcp.calendly.com
```

The LLM doesn't know MCP exists. It calls an AI SDK tool. That tool's `execute()` function happens to use MCP internally. Two layers, one operation.

Same nesting on the booking side, except the LLM isn't involved at all:

```
User clicks time slot in widget      <-- no LLM, pure frontend
  └── POST /api/schedule
        └── createSchedulingLink()   <-- MCP layer
              └── callCalendlyMCP("scheduling_links-create_single_use_scheduling_link")
```

Let me walk through each piece.

### OAuth setup: one-time, runs locally

Calendly's MCP server uses OAuth 2.1 with PKCE and Dynamic Client Registration. That sounds like a lot of acronyms, but in practice it means: no pre-registered app, no client secret, no dashboard configuration. The client registers itself at auth time.

I wrote a one-time setup script that Pablo (me) runs locally:

```javascript
// scripts/calendly-auth.mjs (trimmed)

const clientMetadata = {
  client_name: "dimeglio-dev Guillermo Agent",
  redirect_uris: ["http://localhost:8549/callback"],
  grant_types: ["authorization_code", "refresh_token"],
  scope: "mcp:scheduling:read mcp:scheduling:write",
  token_endpoint_auth_method: "none", // Public client, no secret
};

// Register with Calendly's auth server (no pre-registration needed)
const res = await fetch(metadata.registration_endpoint, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(clientMetadata),
});
const clientInfo = await res.json();
// clientInfo.client_id is all we get — no secret for public clients
```

The script opens a browser for authorization, catches the callback on a local server, exchanges the code for tokens (with PKCE), and stores everything in Upstash Redis. That last part is key: tokens live in Redis, not on disk. Both local dev and Vercel production read from the same Redis instance. Run the script once and both environments work.

### Token management: Redis + optimistic locking

The tokens expire. When they do, the server refreshes them automatically. But in a serverless environment, two requests might try to refresh at the same time. I used Redis `SET NX EX` as a lock:

```typescript
// lib/calendly-mcp.ts — getValidAccessToken() (trimmed)

const tokens = await readTokens(); // from Redis
if (!isExpired(tokens)) return tokens.access_token;

// Try to acquire a 10-second lock
const lockAcquired = await redis.set(REDIS_KEY_LOCK, "1", { nx: true, ex: 10 });

if (!lockAcquired) {
  // Someone else is refreshing — wait and read the updated token
  await new Promise((r) => setTimeout(r, 2000));
  return (await readTokens())?.access_token ?? null;
}

// We got the lock — refresh
const newTokens = await refreshAuthorization(CALENDLY_AUTH_SERVER_URL, {
  metadata,
  clientInformation: clientInfo,
  refreshToken: tokens.refresh_token,
});
await writeTokens({ ...newTokens, obtained_at: Date.now() });
// Lock auto-expires after 10s
```

### The MCP call: connect, call, disconnect

Each MCP call is a fresh connection. No persistent sessions, no connection pooling. This is the right pattern for Vercel serverless where each function invocation is independent:

```typescript
// lib/calendly-mcp.ts — callCalendlyMCP() (trimmed)

const transport = new StreamableHTTPClientTransport(
  new URL("https://mcp.calendly.com"),
  { requestInit: { headers: { Authorization: `Bearer ${accessToken}` } } }
);

const client = new Client(
  { name: "dimeglio-dev-guillermo", version: "1.0.0" },
  { capabilities: {} }
);

await client.connect(transport);
const result = await client.callTool({ name: toolName, arguments: args });
await client.close();
```

Three lines that matter: `connect`, `callTool`, `close`. Everything else is setup and error handling.

### The AI SDK bridge

This is where the two layers meet. The LLM calls `checkAvailability`, which is a standard AI SDK tool. Inside its `execute()` function, we call MCP:

```typescript
// app/api/chat/route.ts — checkAvailability tool (trimmed)

checkAvailability: {
  description: "Check Pablo's calendar availability...",
  execute: async (args) => {
    const tz = args.timezone || "America/New_York";
    const slots = await fetchAvailableSlots(); // ← MCP happens here
    if (!slots) {
      // MCP failed — return fallback props
      return { days: [], timezone: tz, fallbackUrl: CALENDLY_FALLBACK_URL };
    }
    // Group raw ISO slots by day, format labels in user's timezone
    return { days: groupSlotsByDay(slots, tz), timezone: tz };
  },
}
```

The return value becomes an `AvailabilityPicker` widget in the chat. The LLM writes one sentence of text ("Here are Pablo's available slots"). The widget handles everything visual.

### Booking: the LLM is not involved

When the user clicks a time slot, the widget POSTs directly to `/api/schedule`. No LLM in the loop:

```typescript
// components/chat/availability-picker.tsx (trimmed)

async function handleSlotClick(startTime: string) {
  const res = await fetch("/api/schedule", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ startTime, timezone }),
  });
  const data = await res.json();
  // data.url = single-use Calendly scheduling link (from MCP)
  setBookingUrl(buildCalendlyUrl(data.url, startTime, timezone));
}
```

The `/api/schedule` endpoint calls `createSchedulingLink()`, which makes another MCP call to generate a single-use Calendly link. The user clicks through to Calendly to complete the booking.

## Where MCP's standard flow broke down

This is the part that matters if you're evaluating MCP for your own production app. Four places where the textbook approach didn't work.

### 1. We don't use `listTools`

Standard MCP architecture: call `client.listTools()` to discover what the server offers, pass those tools directly to the LLM, let it call them. Dynamic tool discovery is one of MCP's best features.

We skip all of that. We hardcode the two tool names we need and call them manually from inside AI SDK `execute()` functions.

Why? If we passed MCP tools through to the LLM, Calendly's raw JSON slot data would reach the model. And the model would describe every time slot as text: "Available slots: Monday 9:00 AM, 9:30 AM, 10:00 AM..." instead of rendering the interactive picker widget.

We needed MCP for transport and auth (OAuth 2.1, Streamable HTTP, token refresh) but the AI SDK for tool dispatch. I've been calling this the "bridge pattern" because the AI SDK tool's `execute()` function is literally a bridge between the two systems.

### 2. No time pre-selection on single-use links

I expected: generate a scheduling link that opens Calendly on the exact time slot the user picked. What actually happens: Calendly's single-use links (`/d/xxxx`) ignore all time-related URL parameters.

I tried `?time=09:30` (silently ignored), path-based ISO timestamps like `/d/xxxx/2026-04-21T09:00:00-07:00` (also ignored), and various combinations. Only `?date=YYYY-MM-DD` works for pre-selecting the date.

The workaround: pre-navigate to the correct date and show the selected time in the UI with instructions: "Select 9:30 AM on Calendly to confirm." One extra click. This is a Calendly limitation, not an MCP one.

### 3. No direct booking on the free plan

A real scheduling agent should book the slot on behalf of the user. Calendly's `create_invitee` tool would do this, but it's not available on the free plan.

The workaround: single-use scheduling links. MCP creates a link that can only be used for one booking. But the slot isn't held between when the user clicks and when they complete the booking on Calendly. Someone else could theoretically grab it. The "single-use" property is about the link, not the slot.

### 4. OAuth scopes are completely siloed

MCP scopes (`mcp:scheduling:read`, `mcp:scheduling:write`) and Calendly's REST API scopes (`event_types:read`, etc.) are completely separate. You can't use the MCP token to call `api.calendly.com` directly. Everything has to go through MCP tools.

This caught me during the auth setup script. I needed to list event types to find the right URI. My first attempt used the REST API, which returned 403 (insufficient scope). I had to use the MCP tool `event_types-list_event_types` instead.

## The small model prompt problem

One last thing. The system prompt originally said: "do NOT describe time slots as text." And GPT-4o-mini, the model powering Guillermo, dutifully listed every time slot as text in its response.

Small models treat negative constraints as templates. Tell them "don't list times" and they read "list times." The fix was positive prescription: "Your text response must be exactly one short sentence like 'Here are Pablo's available slots.'" That worked immediately.

This pairs with the `listTools` deviation above. Even if we'd passed raw slot data through MCP to the LLM, we'd still have needed to solve the prompt problem. The widget approach sidesteps both issues at once.

## What I'd tell someone building with MCP in production

MCP worked for this. The OAuth + transport + tool calling layer is solid. The `@modelcontextprotocol/sdk` made the connection to `mcp.calendly.com` straightforward. Token refresh, PKCE, Streamable HTTP transport: it all works as documented.

But "MCP in production" means making architectural trade-offs the protocol spec doesn't cover. Where does the LLM boundary sit? Do you pass tools through dynamically or hardcode them? How do you handle visual rendering when the protocol is designed for text? Those are the questions I spent most of my time on. Not the MCP parts.

The "Schedule a Call" button works now. It took about a day, and most of that was fighting Calendly's URL parameters, not MCP.
